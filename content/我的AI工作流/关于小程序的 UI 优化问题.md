# 关于小程序的 UI 优化问题

## 一句话结论

拿到一个完整的前后端小程序后，如果想让 AI 优化 UI，不建议一开始就让 AI 直接改现有源码。

更稳的做法是：

1. 先把源码交给一个偏工程分析的 AI，让它盘点主要页面和子页面。
2. 让它输出页面清单，包含页面名称、路径、层级和主要功能。
3. 再把这份页面清单发给专门做 UI 的 AI Agent，让它们基于页面列表做原型和视觉方案。
4. 等视觉风格、信息层级和交互流程确认后，再把改动回写到小程序页面里。

这样可以把“设计优化”和“业务逻辑改造”拆开，减少 AI 改坏功能的风险。

## 问题背景

现在的难点不一定只是“AI 会不会写 WXSS”。真正的问题可能在几个地方：

- 微信开发者工具的预览、调试和截图链路不适合快速做视觉迭代。
- 小程序页面里的结构、样式、接口请求、状态管理可能耦合在一起。
- AI 看到的是代码，不一定能准确还原真实页面层级和用户路径。
- 如果没有明确的视觉目标，AI 很容易只改颜色、间距和圆角，而不是重新处理信息层级。

所以这件事不能只当成“让 AI 美化页面”。它更像一个小型重构：先把 UI 从业务代码里拆出来，再决定怎么落回去。

## 为什么不直接改源码

直接让 AI 修改小程序源码，主要有四个风险：

- **理解偏差**：AI 可能误判 WXML、WXSS、组件、页面路由之间的关系。
- **功能回归**：样式改动可能影响按钮、弹窗、表单、接口状态和页面跳转。
- **验证成本高**：每次修改都要进微信开发者工具预览，反馈速度慢。
- **目标不清晰**：没有原型或截图对照时，很难判断“优化”到底优化了什么。

如果项目已经有订单、支付、登录、门店、配送等核心流程，这种风险会更明显。

## 推荐流程

### 1. 让 AI 分析源码里的页面结构

先把完整源码交给一个偏工程分析的 AI，让它不要改代码，只做页面结构盘点。

需要它回答几个问题：

- 这个小程序有多少个主要页面？
- 每个主要页面下面有多少个子页面？
- 页面之间是什么层级关系？
- 哪些页面属于核心业务流程？
- 哪些页面只是设置、说明、个人中心这类辅助页面？

它的输出最好是一张清单，而不是一段笼统描述。

需要记录：

- 页面名称和路径
- 页面层级：主页面 / 子页面
- 所属模块
- 页面入口
- 核心功能
- 用户主要操作
- 是否需要交给 UI Agent 优化

这个步骤的产物是“页面地图”。它不是设计稿，而是后面分发给 UI Agent 的任务边界。

### 2. 整理给 UI Agent 的页面清单

拿到页面地图后，再整理成可以直接发给 UI Agent 的格式。

建议每个页面都包含：

- 页面名称
- 页面路径
- 页面类型：主页面 / 子页面 / 弹窗 / 状态页
- 当前功能说明
- 用户在这个页面要完成什么任务
- 需要重点优化的地方
- 是否需要保留现有业务逻辑

可以让 UI Agent 按页面逐个输出方案，也可以按业务流程输出一组连续页面。比如首页、商品详情、购物车、下单、支付结果，就应该作为一个连续流程处理。

### 3. 提取前端结构

从小程序页面中提取 UI 相关部分：

- 页面结构
- 主要组件
- 样式规则
- 关键交互状态
- 列表、详情、空状态、加载状态、错误状态

这一阶段先不要处理复杂后端逻辑。接口返回可以用静态数据模拟，只保留影响界面的字段。

### 4. 做独立 UI 原型

让 AI 基于提取出来的页面结构做一个可看的原型。

可选形式：

- HTML 原型
- 可运行的前端 Demo
- 页面设计稿截图
- 关键流程的多页面 mockup

这一阶段重点看三件事：

- 信息层级是否更清楚
- 用户操作路径是否更顺
- 视觉风格是否适合业务场景

不要急着追求代码完全兼容小程序。原型的作用是先把方向看明白。

### 5. 回写到小程序

原型确认后，再把设计拆回小程序代码。

回写时应尽量遵守两条线：

- 保留原有业务逻辑、接口调用和页面跳转。
- 只改页面结构、样式和必要的交互状态。

如果某个页面耦合太重，可以先局部重构组件，再替换 UI。不要一次性重写整个页面。

### 6. 在微信开发者工具中验证

每次回写后都要做实际验证：

- 页面是否正常渲染
- 按钮和跳转是否正常
- 接口请求是否正常
- loading、空状态、错误状态是否正常
- 不同屏幕尺寸下是否变形
- 优化前后截图是否能看出差异

## 建议交付物

- 现有页面清单
- 页面层级地图
- 给 UI Agent 的页面任务清单
- 优化前截图
- 独立 UI 原型
- 优化后截图
- 小程序源码改动清单
- 验证记录

## 当前判断

这件事不应该从“让 AI 直接改小程序源码”开始。

更合适的顺序是：先让 AI 从源码里盘点页面，得到主要页面和子页面清单；再把这份清单发给专门做 UI 的 AI Agent，让它们做可评审的原型；最后再把确认后的改动落回小程序源码。

这样不仅能降低业务逻辑被改坏的风险，也更容易判断问题到底出在设计、前端结构，还是微信开发者工具的调试链路上。
