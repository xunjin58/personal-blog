# git 与 vibe coding（整理版）

> [!note]
> 本页是整理版。
> 原始内容未改动，原文见：[[git 与 vibe coding]]

## 核心观点

- 做 `vibe coding` 时，不要忘记 `git`
- `git` 的核心价值是版本管理和回溯
- 可以把常用的 `git` 操作直接写进底层规则文件里，例如 `AGENTS.md` / `CLAUDE.md`

## 一、先建立最基础的存档能力

### 目标

- 给项目创建本地 `git` 仓库
- 完成第一次存档
- 后续每次工作结束都做一次存档

### 可直接给 AI 的指令

```text
帮我给这个项目建一个本地 git 仓库，并完成第一次存档。
```

```text
每次工作结束之后。
用 git 帮我做一次存档，根据我们刚才完成的工作写一个备注；存完之后给我一个这次工作的总结。
```

### 工作流建议

- 每完成一个明确阶段，就提交一次
- 提交信息要写清楚这次做了什么
- 提交后顺手输出一段本次工作的总结，方便回顾

## 二、把提交习惯写进底层规则

### 你的思路

- 把规则写进 `AGENTS.md` / `CLAUDE.md`
- 每完成一个新的东西，就立刻 `commit`
- `commit` 时顺手写备注

### 这样做的意义

- 不靠临时记忆
- 让 AI 默认执行版本管理
- 降低忘记存档的概率

## 三、把 git 当成“回档功能”

### 用途

- 查看最近的存档记录
- 退回到上一个存档状态

### 可直接给 AI 的指令

```text
用 git 帮我查看最近的存档记录，退回到上一个存档的状态。
```

## 四、多任务并行时，靠分支隔离

### 场景

假设同时有三件事：

- 一个新功能做了一半
- 另一个功能刚做完还没上线
- 线上版本突然出了一个 bug 需要修

### 关键方法

这时候要用 `Git` 的**分支功能**。

### 理解方式

- `main`：主线版本，线上正在运行的稳定版
- `branch`：单独拉出来开发的新线，彼此互不干扰

## 五、分支操作的标准动作

### 1. 创建新分支开发功能

```text
用 git 帮我创建一个新分支，来开发这个功能，不要改动主线。
```

### 2. 功能完成后合并回主线

```text
这个功能已经测试没问题了，用 git 帮我合并到主线。
```

### 结果

- `C` 功能做完后可以直接合并上线
- `A` 和 `B` 继续在各自分支开发
- 彼此互不影响

## 六、这篇笔记可以沉淀成的最小规则

1. 任何项目开始时，先初始化本地 `git`
2. 每次完成一个阶段，就做一次提交
3. 提交信息必须对应刚完成的工作
4. 需要并行处理多件事时，优先开分支，不直接改 `main`
5. 需要回退时，先看历史，再决定回到哪个存档

## 七、适合沉到系统提示词里的版本

```text
你在当前项目里默认使用 git 做版本管理。
1. 如果项目还没有 git 仓库，先初始化，并完成第一次提交。
2. 每次完成一个明确的小阶段，就主动建议或直接执行一次提交。
3. 提交信息要准确描述刚完成的工作。
4. 提交完成后，输出本次工作的简短总结。
5. 如果当前任务不应影响主线，先创建新分支再开始开发。
6. 如果我要回退版本，先展示最近的提交记录，再执行回退。
```
